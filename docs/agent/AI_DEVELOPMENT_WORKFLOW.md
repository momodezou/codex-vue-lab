# AI 辅助开发工作流

每次任务从明确验收条件和变更权限开始。开发者负责业务判断和发布授权，Agent 负责在授权范围内调查、实现、验证并提供可追溯证据。现有任务可直接套用仓库模板。 [项目规则](../../AGENTS.md) · [任务模板](TASK_TEMPLATE.md)

## 从需求到提交

按表格自上而下推进。发现缺陷时从修复环节返回 Diff 审查和自动化测试，再以候选提交为单位确认质量和验收结果。

| 阶段 | 输入 | Agent 负责 | 开发者负责 | 输出与完成标准 |
| --- | --- | --- | --- | --- |
| 1. 需求分析 | 业务目标、问题描述或 Issue | 把目标转换成可观察行为，找出需要明确的边界和非目标 | 确认预期、优先级、数据范围与允许的操作 | 得到可验收的任务描述。每条验收条件都能通过可执行用例或人工操作检查 |
| 2. 项目上下文读取 | 项目规则、上下文、交接、当前工作区 | 核对入口、调用方、相关测试、分支、基准 SHA 和现有改动，标出文档与现状的差异 | 补齐仓库里没有的业务约定，处理存在冲突的工作区归属 | 得到源码及测试入口、基准提交、变更边界和待确认项。可追溯到文件或工具记录 |
| 3. 技术方案设计 | 验收条件、现有架构和数据约束 | 选定最小实现路径，说明状态归属、数据流、边界和回归风险 | 确认用户可见行为、契约变更和重大取舍 | 得到方案要点、影响文件和验证设计。既有调用路径和需保持的行为都有交代 |
| 4. 任务拆分 | 技术方案、环境、验收条件 | 按依赖拆出实现、测试、审查和发布步骤，标注权限及阻塞点 | 确认可交付范围和需要本人确认的动作 | 得到有顺序的任务清单。每项有可观察产物，审批步骤清晰 |
| 5. Agent 代码修改 | 任务清单、授权文件、项目风格 | 在确认的分支上复用现有逻辑，完成代码和对应测试 | 处理有争议的行为，授权必要的范围变更 | 得到有针对性的代码与用例。主流程经过正常入口，变更集中在允许范围 |
| 6. Git Diff 审查 | 基准 SHA、工作区或候选提交、验收清单 | 核对 Diff、状态修改、类型和事件契约、遗漏的边界与无关文件 | 确认可接受风险，检查关键逻辑及业务判断 | 得到带文件位置的审查结论。阻塞问题已处理，Diff 逐项对应需求 |
| 7. 自动化测试 | 已审查的改动、依赖与浏览器环境、测试脚本 | 运行相关单测、组件测试、E2E、Lint 和 Build，记录退出码与实际范围 | 确认必须通过的检查和可接受的环境限制 | 得到命令、SHA 或工作区范围、结果及未运行项。每项结果有执行输出 |
| 8. Bug 修复 | 失败断言、可复现操作、日志或 trace | 先复现，再区分产品缺陷、测试缺陷和环境问题。按根因做最小修复并回归 | 确认期望行为，决定需要推迟的缺陷及影响 | 得到复现记录、根因、补丁与复跑结果。失败场景和相关回归均已核对 |
| 9. CI 验证 | 工作流配置、候选 SHA、运行记录或本地质量结果 | 发布前核对本地质量基线。发布后查同一候选提交的 Actions 事件、job 和失败步骤 | 授权远端操作，确认仓库的合并门槛 | 得到候选提交的 CI 状态与运行链接。待发布时标为「未触发」，实际成功以对应 job 为准 |
| 10. 人工验收 | 验收清单、测试环境、候选版本 | 提供复现步骤、测试数据、预期结果和自动化范围以外的检查点 | 用实际界面核对体验，确认例外并给出验收结论 | 得到逐项验收记录和版本标识。每项都注明通过、失败或延期及其原因 |
| 11. Git 提交与 PR | 已审查 Diff、候选资格、Issue、发布授权 | 准备清晰提交与 PR 描述。按授权执行 Git 操作，追踪 PR CI 与 Review | 决定提交和推送范围，确认 PR 目标、评审与合并 | 本地有可追溯提交，远端有确定的 PR、对应 CI 和最终评审状态。合并由开发者决定 |

第 9 步有前后两次检查。第 11 步推送候选提交后，GitHub 才能为该版本运行远端 CI。获取结果后回到第 9 步，并按第 10 步复核验收。候选提交变更时，把审查、CI 和验收证据绑定到更新后的版本。 [CI 触发条件](../../.github/workflows/ci.yml)

## 可复制的任务输入

| 字段 | 例子 |
| --- | --- |
| 要解决的问题 | 用户管理需要一次清空关键词、恢复全部状态并回到第一页 |
| 必须保留的行为 | 每页条数、用户数据、原有查询和分页行为 |
| 验收场景 | 组合筛选后位于第二页、当前无结果、默认筛选下位于第二页 |
| 相关入口 | 用户管理页面、列表纯函数、组件测试、Chromium E2E |
| 修改与权限边界 | 修改页面和对应测试，外部发布动作逐项授权 |
| 交付证据 | Diff、实际命令结果、提交 SHA、PR 与 CI 运行链接 |

把使用场景和可观察的验收状态写进任务。「清空关键词」可以直接在浏览器验证输入为空。「用户数据保留」可以先新增或编辑一条临时测试数据，再重置并检查该记录。 [任务模板](TASK_TEMPLATE.md) · [Issue #1](https://github.com/momodezou/codex-vue-lab/issues/1) · [E2E 用例](../../tests/e2e/user-management.spec.ts)

## 执行记录与交接

每项检查记录 `版本或工作区 / 命令 / 环境 / 退出码或服务状态 / 结论`。这个项目的质量命令为 `npm test`、`npm run test:e2e`、`npm run lint` 和 `npm run build`。覆盖率与跨浏览器检查按验收范围记录。Playwright E2E 使用浏览器测试脚本，MCP 浏览器观察则记录实际工具名、页面或快照以及调用状态。 [项目脚本](../../package.json) · [Playwright 配置](../../playwright.config.ts)

交接优先记录稳定事实及变更范围，再记录最后一次执行和剩余事项。提交前留一份 Diff 审查结论。PR 中写明摘要、改动、实测结果、风险和真实 Issue。GitHub 读权限与写权限分别验证。写入被拒绝时保留错误和草稿，由具备权限的开发者完成发布。下一次会话用最新 Git 和远端记录核实交接快照。 [项目上下文](PROJECT_CONTEXT.md) · [历史交接](HANDOFF.md) · [PR #2](https://github.com/momodezou/codex-vue-lab/pull/2)
